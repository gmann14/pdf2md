# Implementation plan — pdf2md

Regenerated by the Forge plan pass from `docs/` ↔ code gap analysis. Hand-edits
survive only until the next plan pass; durable direction belongs in `docs/`.

Item statuses: `open | in-progress | escalate | blocked | done`
Open items are listed in priority order (highest first). Ids are stable.

## Context

The project is far along. Phase 1 MVP, Phase 1.5 (`@pdf2md/core@0.2.0`), and
Phase 1.6 (`@pdf2md/mcp@0.1.0` + Claude skill) are shipped and published. The
conversion engine already implements the full spec contract (`ConversionResult`,
stable codes, `AbortSignal`, progress, metadata/YAML front matter) plus most of
Phase 2 (tables, code blocks, multi-column, multi-file drop). Quality sits at
~9.0/10 across 28 corpus PDFs with 97 unit tests. The site is live on Vercel
with SEO meta, JSON-LD, OG image, how-to content, and a privacy page.

Shipped this cycle: pdf2md#1 (observability, hand-rolled Sentry envelope +
cookie-free analytics) and pdf2md#2 (CI pipeline + corpus smoke). A Playwright
E2E suite now runs as a Forge gate against the prod export — and it surfaced the
top new gap below (#10): conversion is broken under `next dev`.

The gaps below are the verified remainder, prioritized for a launch-imminent
project. Each "not implemented" claim was reconfirmed by code search this pass,
not assumed.

## pdf2md#10 — Fix PDF.js worker init so conversion works under `next dev`
- **Description:** Uploading any PDF in `next dev` throws `Object.defineProperty called on non-object` ("Processing Error"); the prod static export converts the same PDF fine. Root cause is the worker URL resolution in `packages/core/src/pdf-worker.ts` (`new URL("pdfjs-dist/build/pdf.worker.min.mjs", import.meta.url)`) behaving differently under the dev server, with `apps/web/next.config.ts` only aliasing `canvas`. Broken local dev blocks all manual testing.
- **Acceptance criteria:**
  - `pnpm dev` converts a real PDF end-to-end with no `Object.defineProperty` / worker error; output matches the prod export for the same file.
  - Worker loads correctly in both `next dev` and the static export (no regression to `pnpm build`).
  - Existing Playwright E2E gate (runs against the prod export) stays green; optionally add a cheap dev-mode smoke if it does not slow the gate materially.
  - `pnpm typecheck` and `pnpm test` pass.
- **Complexity:** med
- **Spec:** Not in spec — regression found by the E2E gate. Relates to `docs/spec.md` §architecture (PDF.js Web Worker, client-side).
- **Inbox:** `feedback/archive/fb-2026-06-20-001.md`
- **Status:** open

## pdf2md#9 — Dark mode toggle
- **Description:** Add a light/dark theme toggle to the web app. Confirmed absent: `globals.css` is a bare `@import "tailwindcss"`, and there is zero `dark:`/`prefers-color-scheme`/`theme` usage anywhere in `apps/web/src`. Not in `docs/spec.md` — this is user feedback (`fb-2026-06-18-001`).

- **Complexity:** low

## pdf2md#4 — Tagged-PDF fast path via getStructTree()
- **Description:** When a PDF exposes a structure tree (`page.getStructTree()`), use it for semantic-accurate conversion instead of pure heuristics. Confirmed absent: no `getStructTree`/`StructTree` reference anywhere in core or web.

  - New unit tests cover tagged and tag-fallback cases; `pnpm test` and `pnpm typecheck` pass.
- **Complexity:** high
- **Spec:** `docs/spec.md` Phase 2 feature 8 "Tagged PDF fast path"; Phase 2 checklist (open).
